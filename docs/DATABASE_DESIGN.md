# PostgreSQL Database Design

## DAS 839 - NoSQL Systems End-Semester Project

## 1. Purpose

PostgreSQL is the common reporting database for all four ETL pipelines:

1. Apache Pig
2. Hadoop MapReduce
3. MongoDB
4. Apache Hive

The Python controller loads the JSONL outputs produced by the selected backend into PostgreSQL.

PostgreSQL is used for reporting and metadata persistence. It does not replace the ETL processing performed by the selected backend.

PostgreSQL 15 or later is assumed.

## 2. Database

Database name: `nosql_final_project`

| Table | Purpose |
|---|---|
| `runs` | Execution metadata, configuration, environment and run status |
| `run_batches` | Per-batch record statistics |
| `phase_timings` | Optional diagnostic phase durations |
| `malformed_samples` | Retained malformed examples |
| `q1_daily_traffic` | Q1 daily traffic results |
| `q2_top_resources` | Q2 top resource results |
| `q3_hourly_errors` | Q3 hourly error results |

Every child table has a foreign key to `runs(run_id)` with `ON DELETE CASCADE`.

## 3. Runs Table

Table: `runs`. One row represents one pipeline execution attempt, including failed attempts.

| Column | PostgreSQL type | Description |
|---|---|---|
| `run_id` | `UUID PRIMARY KEY` | Generated by the controller |
| `pipeline_name` | `VARCHAR(30) NOT NULL` | `Pig`, `MapReduce`, `MongoDB` or `Hive` |
| `batch_size` | `BIGINT NOT NULL` | Configured maximum batch size |
| `status` | `VARCHAR(20) NOT NULL` | `RUNNING`, `FAILED` or `COMPLETED` |
| `started_at` | `TIMESTAMPTZ NOT NULL` | UTC execution start, captured when the timer starts |
| `completed_at` | `TIMESTAMPTZ NULL` | Set together with `status = 'COMPLETED'` |
| `results_committed_at` | `TIMESTAMPTZ NULL` | Durable result-transaction marker for planned recovery |
| `elapsed_seconds` | `DOUBLE PRECISION NULL` | Authoritative measured runtime |
| `total_records` | `BIGINT NULL` | Total input records |
| `total_batches` | `BIGINT NULL` | Number of non-empty batches |
| `malformed_count` | `BIGINT NULL` | Total malformed records |
| `average_batch_size` | `DOUBLE PRECISION NULL` | `total_records / total_batches`; NULL for empty input |
| `input_files` | `JSONB NOT NULL` | Ordered input filenames with size in bytes and SHA-256 |
| `engine_info` | `JSONB NULL` | Backend name, version and execution mode (for example local or pseudo-distributed) |
| `environment` | `JSONB NULL` | Host OS, CPU, memory, container image or other relevant notes |
| `error_message` | `TEXT NULL` | Failure details for `FAILED` runs |

Checksums in `input_files` come from the input verification step in `EXPERIMENT_DESIGN.md` section 3. That step runs before benchmarking and outside any timed run, and its values are copied into each run row.

Constraints:

- `CHECK (pipeline_name IN ('Pig', 'MapReduce', 'MongoDB', 'Hive'))`
- `CHECK (status IN ('RUNNING', 'FAILED', 'COMPLETED'))`
- `CHECK (batch_size > 0)`
- `CHECK (elapsed_seconds IS NULL OR elapsed_seconds >= 0)`
- `CHECK (status <> 'COMPLETED' OR (elapsed_seconds IS NOT NULL AND completed_at IS NOT NULL))`

## 4. Run Batches Table

Table: `run_batches`. One row represents one non-empty batch.

| Column | PostgreSQL type | Description |
|---|---|---|
| `run_id` | `UUID NOT NULL` | References `runs` |
| `batch_id` | `INTEGER NOT NULL` | Batch identifier, `CHECK (batch_id > 0)` |
| `record_count` | `BIGINT NOT NULL` | Actual input records in the batch, `CHECK (record_count > 0)` |
| `malformed_count` | `BIGINT NOT NULL` | `CHECK (malformed_count BETWEEN 0 AND record_count)` |

Primary key: `(run_id, batch_id)`.

The record count is the actual number of input records assigned to the batch, not the configured maximum batch size. The loader checks that batch IDs are exactly `1..n` with no gaps.

## 5. Phase Timings Table

Table: `phase_timings`. Optional diagnostic timings, loaded from the optional `phase_timings.jsonl` adapter output.

| Column | PostgreSQL type | Description |
|---|---|---|
| `timing_id` | `BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY` | Timing record identifier |
| `run_id` | `UUID NOT NULL` | References `runs` |
| `phase_name` | `VARCHAR(50) NOT NULL` | Name of measured phase |
| `duration_seconds` | `DOUBLE PRECISION NOT NULL` | `CHECK (duration_seconds >= 0)` |

Phase timings are diagnostic. The authoritative benchmark duration is `runs.elapsed_seconds`.

## 6. Malformed Samples Table

Table: `malformed_samples`. Stores the first 100 malformed examples per run in input order.

| Column | PostgreSQL type | Description |
|---|---|---|
| `run_id` | `UUID NOT NULL` | References `runs` |
| `record_number` | `BIGINT NOT NULL` | Continuous input record number |
| `batch_id` | `INTEGER NOT NULL` | Batch of the record; `(run_id, batch_id)` references `run_batches` |
| `source_file` | `TEXT NOT NULL` | Original input filename |
| `reason` | `VARCHAR(20) NOT NULL` | Reason code from `PARSING_RULES.md` section 9 |
| `raw_line` | `TEXT NOT NULL` | Original line after line-terminator removal |

Primary key: `(run_id, record_number)`.

`CHECK (reason IN ('BLANK_LINE', 'NUL_BYTE', 'BAD_STRUCTURE', 'BAD_HOST', 'BAD_TIMESTAMP', 'BAD_STATUS', 'BAD_BYTES'))`

PostgreSQL `TEXT` cannot contain U+0000. When loading a sample, the controller replaces each U+0000 in `raw_line` with the six characters `\u0000`. This affects only the stored sample text, never parsing or analytics.

The sample limit applies only to retained examples. The total malformed count includes every malformed record.

## 7. Common Result Columns

Every result table starts with these columns. The brief requires stored results to include the pipeline name, run identifier, batch identifier and time of execution.

| Column | PostgreSQL type | Description |
|---|---|---|
| `run_id` | `UUID NOT NULL` | References `runs` |
| `pipeline_name` | `VARCHAR(30) NOT NULL` | Copied from `runs.pipeline_name` |
| `batch_id` | `INTEGER NULL` | Positive batch ID, or NULL for a whole-run result |
| `executed_at` | `TIMESTAMPTZ NOT NULL` | Copied from `runs.started_at` |

`(run_id, batch_id)` is a foreign key to `run_batches`. With PostgreSQL's default `MATCH SIMPLE`, the check is skipped when `batch_id` is NULL, so whole-run rows are allowed.

## 8. Q1 - Daily Traffic Table

Table: `q1_daily_traffic`. Common result columns, then the brief's columns in order:

| Column | PostgreSQL type | Description |
|---|---|---|
| `log_date` | `DATE NOT NULL` | Request date |
| `status_code` | `INTEGER NOT NULL` | HTTP response status, `CHECK (status_code BETWEEN 0 AND 999)` |
| `request_count` | `BIGINT NOT NULL` | Number of requests |
| `total_bytes` | `BIGINT NOT NULL` | Sum of bytes transferred |

Uniqueness: `(run_id, batch_id, log_date, status_code)`.

## 9. Q2 - Top Resources Table

Table: `q2_top_resources`. Common result columns, `rank`, then the brief's columns in order:

| Column | PostgreSQL type | Description |
|---|---|---|
| `rank` | `INTEGER NOT NULL` | Position within its scope, `CHECK (rank BETWEEN 1 AND 20)` |
| `resource_path` | `TEXT NOT NULL` | Exact resource path |
| `request_count` | `BIGINT NOT NULL` | Number of requests |
| `total_bytes` | `BIGINT NOT NULL` | Sum of bytes transferred |
| `distinct_host_count` | `BIGINT NOT NULL` | Number of unique requesting hosts |

Uniqueness: `(run_id, batch_id, resource_path)` and `(run_id, batch_id, rank)`.

Reports display rows with `ORDER BY rank`. The rank comes from the backend's binary UTF-8 ordering. Do not re-sort by `resource_path` in PostgreSQL unless you use `COLLATE "C"`, because the database's default collation can break ties differently.

Only resources with a non-NULL path are included. Whole-run distinct-host counts must be calculated across the complete input dataset.

## 10. Q3 - Hourly Errors Table

Table: `q3_hourly_errors`. Common result columns, then the brief's columns in order:

| Column | PostgreSQL type | Description |
|---|---|---|
| `log_date` | `DATE NOT NULL` | Request date |
| `log_hour` | `INTEGER NOT NULL` | `CHECK (log_hour BETWEEN 0 AND 23)` |
| `error_request_count` | `BIGINT NOT NULL` | Requests with status 400-599 |
| `total_request_count` | `BIGINT NOT NULL` | All valid requests, `CHECK (total_request_count > 0)` |
| `error_rate` | `NUMERIC(20,12) NOT NULL` | `CHECK (error_rate BETWEEN 0 AND 1)` |
| `distinct_error_hosts` | `BIGINT NOT NULL` | Unique hosts among error requests |

Also `CHECK (error_request_count <= total_request_count)` and `CHECK (distinct_error_hosts <= error_request_count)`.

Uniqueness: `(run_id, batch_id, log_date, log_hour)`.

Cross-pipeline comparisons use an absolute error-rate tolerance of `1e-9`.

## 11. Handling NULL Batch IDs

A NULL `batch_id` identifies a whole-run result. A positive `batch_id` identifies a per-batch result. Do not use zero or another artificial value.

Enforce the uniqueness rules in sections 8-10 with `UNIQUE NULLS NOT DISTINCT` (PostgreSQL 15+), so that two whole-run rows with the same key are rejected. Example for Q1:

```sql
ALTER TABLE q1_daily_traffic
  ADD CONSTRAINT uq_q1 UNIQUE NULLS NOT DISTINCT (run_id, batch_id, log_date, status_code);
```

On PostgreSQL versions before 15, use two partial unique indexes instead. One covers the full key `WHERE batch_id IS NOT NULL`; the other leaves out `batch_id` and uses `WHERE batch_id IS NULL`.

## 12. Run Lifecycle and Transactional Loading

The controller performs these steps for every run.

Before the timer starts (not measured):

1. Validate the pipeline, batch size and input verification record.
2. Generate the run ID and create a fresh output directory.

Measured run:

3. Capture `started_at` (UTC) and start the monotonic timer.
4. Insert the `runs` row with `status = 'RUNNING'` and commit, so that a failure can always be recorded.
5. Launch the adapter subprocess.
6. Check the adapter exit status and validate all required JSONL files.
7. In one transaction:
   - insert batch statistics, malformed samples, phase timings, and all Q1, Q2 and Q3 rows;
   - update the run-level counts (`total_records`, `total_batches`, `malformed_count`, `average_batch_size`);
   - set results_committed_at in the same transaction;
   - commit.
8. Stop the timer after commit acknowledgement.

After the timer stops:

9. In one statement, set `elapsed_seconds`, `completed_at` and `status = 'COMPLETED'`.

### Completion publication and recovery contract

The controller implementation will hold a dedicated PostgreSQL session-level
advisory lock for the run UUID for the entire attempt. Acquire it before
creating the RUNNING row and release it only after publication or failure
handling. Recovery must try the same lock and skip runs owned by another
session. Starting a controller is never sufficient evidence that other
RUNNING runs have crashed.

Immediately after the result commit acknowledgement, stop the monotonic timer.
Atomically save run_id, elapsed_seconds and completed_at in completion.json
in the run work directory, then update completion metadata and status together.
The completion file is outside the measured interval and must survive until
publication or recovery succeeds.

Failure cases are distinct:

- Before the result commit, roll back the open transaction and record FAILED.
- After commit, keep committed rows hidden while the run remains RUNNING.
  A failed publication can be retried using the durable completion file.
- For an abandoned run whose session lock is free, valid completion metadata
  plus results_committed_at permits publication as COMPLETED.
- If exact completion metadata is unavailable, mark the abandoned run FAILED
  and retain committed rows for diagnosis. Exclude them from all reports
  and benchmarks. Never reconstruct elapsed time from database timestamps.

A lost connection can make commit outcome uncertain. Check the durable marker
during recovery instead of assuming the transaction rolled back.
These are shared design requirements for the later controller/loader phase;
this schema/document update does not implement those application components.

Inserting the `RUNNING` row (step 4) is a single small commit inside the measured interval, and it is the same for every pipeline.

## 13. Relationships

- `runs` (1) to (many) `run_batches`
- `runs` (1) to (many) `phase_timings`
- `runs` (1) to (many) `malformed_samples`
- `runs` (1) to (many) `q1_daily_traffic`, `q2_top_resources`, `q3_hourly_errors`
- `run_batches` (1) to (many) per-batch result rows and malformed samples, through `(run_id, batch_id)`

## 14. Reporting Usage

The Streamlit application reads PostgreSQL to display:

- Run history, including failed runs and their error messages.
- Pipeline, batch size, runtime and average batch size.
- Batch statistics, malformed-record counts and samples.
- Q1, Q2 and Q3 results, per batch and whole run.
- Comparisons between pipeline runs.

Benchmark and result views include only runs with `status = 'COMPLETED'`. NULL batch IDs are displayed as `Whole run`.

All four pipelines use the same database schema and reporting queries.
